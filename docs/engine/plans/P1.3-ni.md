## Цель

Портировать числовой итератор SPICE3F4/XSPICE: ньютоновский цикл `NIiter`,
критерий сходимости `NIconvTest` (+ `CKTconvTest`), коэффициенты интеграции
`NIcomCof`, корректор `NIintegrate` (трапеция/Gear) и драйвер LTE-шага
`CKTtrunc`. После P1.3 ядро умеет решать нелинейную систему и интегрировать
реактивные элементы; устройства (P1.4+) только штампуют матрицу и состояния.

## Границы (что не входит)

- Реализации устройств и их `DEVload`/`DEVconvTest`/`DEVtrunc` — P1.4–P1.6.
  В P1.3 проверяем на синтетических device-хуках.
- Анализы `OP`/`TRAN` (сборка режима, шаг по времени, accept/reject) — P1.6;
  `AC`/`NIdIter`/`NIpz*`/`NIsenReinit` — P3.
- `NIpred` и `CKTagp`/`CKTpred`/`CKTsols`: в обеих сборках (`spice3f4`,
  `xspice-1-0`) `PREDICTOR` **не определён** — код в DLL не компилируется.
  Не портируем; при включении предсказателя — отдельный подпункт.
- Ветка `NEWTRUNC` (LTE по узлам) не компилируется (`NEWTRUNC` не определён):
  LTE считается устройствами через `DEVtrunc` (как в DLL).
- XSPICE-расширения `enh->rshunt_data`, MIF-флаги, IPC pause/stop — фаза X/I.

## Решения по ходу порта

| Вопрос | Решение | Почему |
|---|---|---|
| Редакция при расхождении F4 ↔ XSPICE | берём **XSPICE** (`NIiter`, `NIconvTest`, `CKTload`, `CKTconvTest`) | DLL — `XSPICE32`; расхождения с F4 — в квирк-лист (Q-C02…Q-C04) |
| `CKTload`: nodeset/ic | XSPICE: `rhs[node] += value; diag += 1` (без `ZeroNoncurRow`) | так в `CKTload.c` DLL-линии; F4-вариант — Q-C03 |
| `CKTconvTest` | возвращает `1` при `CKTnoncon != 0` | XSPICE-фикс «all DEVconvTest ineffective» (Q-C02) |
| `NIiter` + `MODEUIC` | обмен `rhsOld`/`rhs` и выход, **без** `CKTload` | XSPICE-редакция; F4 вызывает `CKTload` (Q-C04) |
| `NIconvTest` | не трогает `CKTtroubleNode`/`CKTtroubleElt` | XSPICE заменил их на `ENHreport_conv_prob` (P1.3 без `enh`) |
| `NIintegrate` out-параметры | `{error, geq, ceq}` вместо `double*` | в JS нет указателей; соглашение P1.2 |
| `CKTtrunc` | `{error, timeStep}`; `HUGE = 1.8e308` | в C — `double*`; `HUGE` из `hw_ieee.h` |
| Циклический импорт `ckt ↔ ni` | разрешён: `ckt.js` вызывает NI, `ni.js` — `cktLoad`/`cktConvTest`; используются только внутри функций | ESM-биндинги функций инициализируются до вызова |

## Риски и квирки

- **Q-C02 (открыто):** `CKTconvTest` в F4 возвращает `OK` даже при `CKTnoncon`
  (баг «DEVconvTest ineffective»), в XSPICE — `1`. Берём XSPICE; сверить с DLL
  в P1.6.
- **Q-C03 (открыто):** `CKTload` nodeset/ic: F4 обнуляет строку и ставит
  диагональ в 1/1e10, XSPICE — складывает `rhs += value`, `diag += 1`. Берём
  XSPICE; сверить оракулом (схема с `nodeset`).
- **Q-C04 (открыто):** `NIiter` при `MODEUIC`: F4 вызывает `CKTload`, XSPICE —
  нет. Берём XSPICE; проверить на TRAN с UIC в P1.6.
- **Q-N01 (открыто):** `NIconvTest` XSPICE не выставляет `CKTtroubleNode`
  (диагностика ушла в `ENHreport_conv_prob`). На числа не влияет; вернуть при
  фазе X, если понадобится `CKTtrouble`.
- Циклический импорт `ckt.js ↔ ni.js` — держать вызовы только внутри функций;
  проверяется тестами (импорт модулей не падает).
- Без реальных устройств `CKTtrunc`/`CKTload` проверяются на хуках; настоящая
  LTE-сетка — diff-тест P1.6.
- Новые квирки — в `docs/re/engine-quirks.md` с ID.
