# Формат файлов EWB 5.12 (Electronics Workbench) — reverse engineering

Состояние: 30 % расшифровано (декады Type-1 и Type-2 работают; текстовый формат разбирается).

## 1. Обзор

Файлы `.ewb`/`.cnf` (EWB 5.x) состоят из:

```
<заголовок строк текстом ASCII>  '/'  <закодированное тело>
```

Заголовок (все строки заканчиваются `\r\n`):

```
"Electronics Workbench Circuit File"
"Version: 5"
"Charset: ANSI"
"Description: \r\n\"\" "
"EncryptionType: <1|2>"
"UsingVectorGraphics: <0|1>"
```

Последовательность полей подтверждена декомпиляцией заголовочного парсера
`FUN_004b4c0e` (WEWB32.EXE) и функций сохранения `FUN_0046827b`.

Тип шифрования выбирает алгоритм обработки тела:
- **Type 1** (`UNTITLED.EWB`): простой поток — без сжатия.
- **Type 2** (`DEFAULT.EWB`, все примеры `CIRCUITS/*`): сжатие (LZSS+Хаффман) в 5 секциях.

## 2. Type 1 — простой кодек

Функции: `FUN_00466a1b` (реверс байтов), `FUN_004669e2` (XOR двойными словами),
saver `FUN_0046827b`, reader `FUN_00466ac9`.

### Кодирование тела (как пишет saver)

1. Каждый байт исходника → 2 символа `A`..`P` (нибблы): `c = nibble + 0x41`.
2. Поток разбит на строки: полные строки по 66 символов (64 hex + `\r\n`),
   последняя строка короче (кратна остатку `len % 32`): `2*(len%32)+2` символа.
   Первая строка файла = короткая (остаток), далее полные строки по 66.
3. Перед кодированием на каждый блок применяется transform:
   - `FUN_00466a1b`: реверс всех байтов блока.
   - `FUN_004669e2`: для каждого двойного слова
     `dw ^= param3 ^ egg_dword[roll]`, где
     `param3 = размер всего файла в байтах`,
     `egg = "In the Big Inning, the Jays hit a homer"` (40 байт),
     `egg_dword[roll] = little-endian uint32 по адресу egg[roll]`,
     `roll = 0..36`, сброс при `roll > 0x24` на 0 (свои roll на каждый блок).
   - Блок = 32 байта; последний блок короткий.

### Декодирование (reader)

```
прочитать байты до '/' (или 0x1a)
fileSize = размер файла
lenBody = sizeof(остатка после '/')
первый_чтение = (lenBody % 66) или 66
для каждой строки:
    убрать \r\n
    байт = ((c[i]-'A')<<4) | (c[i+1]-'A')
    для каждого dword: dw ^= fileSize ^ egg_dword[roll]
    реверс байтов
    вывод
```

Проверено: `UNTITLED.EWB` (11707 байт) → 5613 байт текстовой сериализации,
начинающейся с `Project \r\n{ \r\nCircuitHeader \r\n{ ...`.

## 3. Type 2 — сжатый формат

### Уровень 1: символы → байты (ниббл-кодек)

Функции: `FUN_004a9aeb` (чтение ниббла), `FUN_004a9bd8`/`FUN_004a9b67`
(запись), reader строки `FUN_004a9a4d`, сбор байта `FUN_004a9eb3`.

Каждая пара символов даёт один байт сжатого потока:

```
байт = ((c1 - '0') << 3) | ((c2 - '0') >> 2)
```

При кодировании:
- `c1 = '0' + (v >> 3)`  — значения 0..31 → `0`..`?`, `@`, `A`..`O`;
- `c2 = '0' + ((v & 7) << 2)` — значения кратные 4 → `0`,`4`,`8`,`<`,`@`,`D`,`H`,`L`.

Строки тела: 65 символов (64 + `\n`). Символы `\r`/`\n` при чтении пропускаются
(`FUN_004a9a4d`).

EOF-маркеры секции: `!` (0x21) и `$` (0x24). Они разбивают поток на секции.
Контрольная сумма в конце файла пишется символами `%08lx` (`FUN_004a9f35`) и
при декодировании не участвует.

### Уровень 2: inflate (LZSS + Хаффман)

Функции: `FUN_005582bc` (init), `FUN_00558434` (главный цикл),
`FUN_0055851e` (декод токена), `FUN_005586db` (декод расстояния),
`FUN_0055875a` (битовый читатель, порядок LSB-first), таблицы Хаффмана в
`.data` (DAT_0059a44c..0059a45c, 0059a3cc..0059a40c, 0059a47c..0059a48c).

Заголовок каждой секции (3 байта):
- `[0]` = тип: 0 = литералы сырые (байт), 1 = литералы Хаффманом;
- `[1]` = ширина `W` (4..6) — число сырых битов расстояния;
- `[2]` = произвольный байт (уходит в начальное значение битового аккумулятора).

Поток битов — побитовый, LSB-first, 8-bit фиксированный lookahead.

Каждый токен начинается с 1 бита:
- `0` → литерал; для типа 0: 8 сырых бит; для типа 1: Хаффман-литерал
  (таблица на 256 символов, `FUN_0055881d`).
- `1` → совпадение (backref): Хаффман-код длины (16 символов, первичная fast-таблица
  256 записей) + до 8 бит дополнений, затем Хаффман-код расстояния (64 символа)
  + `W` сырых бит.

Значения:
- длина совпадения = `token - 0xfe` (2..517);
- расстояние = `(idx_dist << W) | сырые_bits + 1` (при длине == 2 берётся 2 бита);
- окно скользящее 0x1000 байт (буфер, flush по 0x1000);
- конец потока: токен `> 0x304` (в т.ч. 0x305 — спецмаркер конца, 0x306 — ошибка).

### Многосекционность

Файл Type-2 = последовательность секций, разделённых `!`/`$`. Каждая секция —
самостоятельный сжатый поток (собственный заголовок, LZ-окно сбрасывается).
Декодируется каждая секция отдельно, результаты конкатенируются.

Пример: `DEFAULT.EWB` (4233 байта) → 5 секций
(457, 369, 399, 406, 383 байта сжатых) → 5045 байт текстовой сериализации.

## 4. Текстовый формат сериализации (выход декодера)

Raw-данные — это текстовый поток (Python-подобный):

```
Project \r\n
{ \r\n
  CircuitHeader \r\n
  { \r\n
    InternalCircuitVersion i 502 \r\n
    ...
```

- Строки выровнены продолжением строки `{ ` / `} `.
- Типизированные значения:
  - `i 16` — int;
  - `R "Arial"` — строка/имя;
  - `r 0.01` — double;
  - `i:10 ...` / `r:4 ...` — массив из N значений;
- Версия схемы `InternalCircuitVersion i 502` (UNTITLED) / `511` (DEFAULT); — разобрать позже.

### 4.1 Структура проекта (по `CIRCUITS/**`)

```
Project | Project_5_1                  # тег разнится, см. §4 PLAN.md
{
  CircuitHeader
  {
    InternalCircuitVersion i 511
    ZoomFactor / VersionSpecific { SerialNo, Version, Ewb_Restrictions{...} }
    Library { Name R "$"; Models { Model {...} } }   # дефолтные модели семейств
    Elements { MacroFace {...} ... }                  # определения макро-«лиц»
    PrintSettings {...}
  }
  Circuit
  {
    Models { Model {...} ... }        # модели экземпляров (напр. "2n3xxx:2N3904")
    Preferences { ... }
    Elements { ... }                  # элементы схемы (см. 4.2)
    Wires { wire ... }                # соединения (см. 4.3)
    <Oscilloscope|MultiMeter|FuncGen|...>   # блоки приборов/анализов
  }
}
```

### 4.2 `Circuit.Elements` — элементы и индексное пространство

Дети `Elements` (в порядке файла): `Comp`, `Instrument`, `ExtComp`, `MacroIcon`.
**Индекс провода (`wire.pos`) — 0-based позиция в этом полном списке**, а не «среди
Comp». Проверено по всем `CIRCUITS/**`: у 2-выводных элементов ровно терминалы
0/1, у земли — только 0.

| Блок | Пример | Смысл |
|---|---|---|
| `Comp` | `PartNum i 1 … Common{RefID A "R1"} …` | деталь библиотеки (см. §4.2.1) |
| `Instrument` | `PartNum i 4 Pos i:3 0 1768 894` | прибор на схеме (номера 2..7, соответствие **[?]**) |
| `ExtComp` | `Name R "ANALOG:555" … Common{RefID A "U1"}` | внешняя деталь/ИС из `EXT/*.DLL` (без PartNum) |
| `MacroIcon` | `Name R "7805" Bounds i:4 … Terminal i:4 0 4 2 23 …` | экземпляр макроса из `CircuitHeader.Elements` |

#### 4.2.1 `Comp` — деталь

```
Comp {
  PartNum i <N>                # номер детали (см. docs/re/engine-parts.md)
  Position i:3 0 <x> <y>      # флаги + координаты (шаг сетки ~1 px)
  Value r:<k> <v0> …          # параметр(ы) детали (R=ом, C=фарад, V=вольт…)
  ModelUnits i:<k> <u0> …     # индексы единиц измерения
  Common { RefID A "R5" }     # позиционное обозначение (у земли "0"/пусто)
  ModelName R ""              # имя SPICE-модели ("" = дефолт семейства)
  Status i 0
  m_tptrElem A "R5^0"         # только у служебных узлов-PN39 (см. 4.4)
  m_flags / m_i_cond / m_i_nri
  Label R "…"                 # опционально (у CONN/приборов)
}
```

#### 4.2.2 `Model` — модели

* `Circuit.Models.Model { Name R "2n3xxx:2N3904"; PartNum i 5; Params r:41 … }` —
  модели **экземпляров**, выбранные пользователем (префикс `<lib>:`), параметры в
  порядке SPICE-модели (соответствие — фаза P2) **[?]**.
* `CircuitHeader.Library.Models.Model { Name R "ideal"; PartNum i N; Params r:K … }` —
  «идеальные» дефолты для каждого семейства (PartNum), использованного в схеме.

#### 4.2.3 `MacroFace` — определение макро-подцепи

`CircuitHeader.Elements.MacroFace { Name R "-Vcc"; Bounds i:9 …; Circuit { Elements
{ MacroContact{Pos i:5 …}, Comp… } Wires{…} } }`. Экземпляр ставится как `MacroIcon`
с тем же `Name` и списком `Terminal i:4 <idx> <x> <y> <?>`. В схемах `CIRCUITS/**`
`MacroFace` — способ хранения готовых подсхем/приборов (в т.ч. 7805, компараторы).

### 4.3 `wire` — соединение

```
wire {
  pos i:4 <elemA> <pinA> <elemB> <pinB>   # индексы в Elements + номер вывода (0-based)
  segs i:<k> …                            # точки маршрута (пары x y)
  colour i 0
  wire_id i 0
  node_p A "7"                            # ★ номер электрического узла (строка)
  x_factor / y_factor r …                 # масштаб сегментов
}
```

Правила:

* **электрика — только `node_p`**: провода с одинаковым `node_p` — один узел
  (в т.ч. соединения «через угол» без явного `wire`-point);
* `pos` нужен, чтобы привязать выводы деталей к узлу; `<pin>` — номер терминала
  детали (R/C/L/V/I — 0/1; БТ — 0..2; ОУ PN15 — 0..2; трансформатор PN14 — 0..3;
  `Switch`/реле — 0..3; `Connector` — 0..3 «стороны»; земля — 0);
* `node_p "0"` — земля (символ PN8 «Ground» заземляет все свои точки как 0, при этом
  сам маркер узла для 0 не пишется);

### 4.4 Маркеры узлов `PartNum 39` («Node»)

Отдельный `Comp` PN39 = **маркер номера узла**: `Common.RefID` = номер узла
(числовая строка), `m_tptrElem A "<Ref>^<pin>"` указывает, к какому выводу детали
маркер прикреплён; `Value r:1 0`, `Status`. Инвариант (проверено на 61 схеме):
один маркер на каждый узел ≥ 1; для узла 0 (земля) маркеров нет.

* верхний уровень `Circuit`: `wire.pos` **не** адресует PN39-маркеры (0 из 1931
  проводов) — они только «этикетки» номеров узлов;
* внутри `MacroFace`-подсхем `wire.pos` может ссылаться на PN39-маркеры как на
  концы проводов (там они играют роль узлов-контактов).

### 4.5 Приборы и цифровая часть

* `Instrument { PartNum i <2..7>; Pos i:3 0 x y }` — прибор на листе; в
  `Elements` не несёт параметров (настройки — в блоках `Oscilloscope`/`MultiMeter`/
  `FuncGen`/`LogicAnalyzer`/`Grapher`/`Bode`/`WordGen` внутри `Circuit`).
* Цифровые/сложные детали в схемах представлены `ExtComp` (`Name R "<LIB>:<DETAIL>"`)
  и `MacroIcon`; их внутренности — в `MODELS` (вобьют карточки `.M99` и т.п.) и в
  макро-определениях. Для ядра ключ — PartNum `Comp`-деталей (см. `engine-parts.md`).
